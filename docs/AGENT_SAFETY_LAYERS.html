DQ agent safety layers

What protects the database, the data and the run while the agent works through its trajectory. Every tool call the agent makes crosses three layers on the way to the database: guardrails, verification and a sandbox. Every result crosses them again on the way back. No single layer is trusted on its own.

Guardrails

Policy on what the agent may do, what it may see, and what happens when something goes wrong. These are decisions a person made in advance, enforced outside the model.

PII masking

  • Columns listed under pii: in dq-rules.yml are masked in every result before it enters the model's context.
  • A pattern detector catches PII in columns nobody listed: email, phone, national ID, card numbers.
  • Aggregates pass through unchanged, so COUNT(email) still works. Only row values are masked.
  • The same masking runs on the written report.
email       ana.k@shop.com   → a***@shop.com
phone       +66 81 234 5678  → +66 ** *** **78
national_id 1-1037-01234-56-7 → *-****-*****-**-7

Human-in-the-loop approval

  • Before any query runs, the gate asks the database for a plan estimate (EXPLAIN, never EXPLAIN ANALYZE).
  • Above the thresholds the run pauses and the data steward gets the SQL, the estimate and the reason.
  • No answer within 30 minutes counts as deny. The agent is never left waiting forever.
  • One approval covers one query, not the rest of the run.
approval:
  require_when:
    est_rows_scanned: 5_000_000
    est_runtime: 15m
    budget_used_pct: 80
  approver: data-steward
  timeout: 30m
  on_timeout: deny

Fallbacks

  • Tried in a fixed order, so a failing run degrades the same way every time.
  • Retry with a fix: up to 2 rewrites per rule, only for syntax and unknown-column errors.
  • Narrow the scope: rerun on a sample or one partition. The result is marked sampled in the report.
  • Skip the rule: record status: error with the reason. An error never counts as a pass.
  • Stop and escalate: on permission errors, repeated rejections or an exhausted budget. The partial report is saved.
Verification

Every SQL string the model writes is parsed and checked before it runs. Errors come back as structured hints, so the agent can correct itself without guessing.

SELECT statements only

  • Parse with a real SQL parser in the database's dialect. Never use regex or keyword matching, which comments and quoting can fool.
  • Exactly one statement. SELECT 1; DROP TABLE x is rejected as a whole.
  • The root must be a query (SELECT, WITH … SELECT, UNION).
  • Also rejected, because they look like reads but are not: SELECT … INTO (creates a table) and FOR UPDATE (takes locks).
  • Functions with side effects are deny-listed per dialect, such as pg_sleep, pg_read_file and dblink.
  • A LIMIT is added when the query returns rows rather than an aggregate.
validator sketch · python + sqlglot 
import sqlglot
from sqlglot import exp

DENY = {"pg_sleep", "pg_read_file", "lo_import", "dblink"}
WRITES = (exp.Insert, exp.Update, exp.Delete, exp.Merge,
          exp.Create, exp.Drop, exp.Alter, exp.Command,
          exp.Into, exp.Lock)

def validate(sql: str, dialect: str = "postgres") -> str:
    try:
        stmts = sqlglot.parse(sql, read=dialect)
    except sqlglot.errors.ParseError as e:
        raise Rejected("syntax", e.errors[0]["description"])
    if len(stmts) != 1:
        raise Rejected("multi_statement", "send one statement")
    tree = stmts[0]
    if not isinstance(tree, exp.Query) or tree.find(*WRITES):
        raise Rejected("not_select", "only SELECT is allowed")
    used = {f.name.lower() if isinstance(f, exp.Anonymous)
            else f.sql_name().lower() for f in tree.find_all(exp.Func)}
    if used & DENY:
        raise Rejected("denied_function", sorted(used & DENY))
    if isinstance(tree, exp.Select) and not tree.args.get("limit"):
        tree = tree.limit(1000)
    return tree.sql(dialect=dialect)

Sandboxed execution

The last line of defence. Even if the model asks for something harmful and the validator misses it, the environment cannot do it.

A database-only toolbox

  • The agent sees three tools: list_tables, describe_table and execute_sql. It has no shell, web fetch or file tools.
  • The toolbox is specific to one SQL dialect. The validator, deny-list and catalog queries match the engine behind it.
  • The tool process runs in a container whose only network route is the database host and port.
// .claude/settings.json
{
  "permissions": {
    "allow": ["mcp__dbhub__execute_sql",
              "mcp__dbhub__search_objects"],
    "deny":  ["Bash", "WebFetch", "WebSearch",
              "Write(./**)", "Edit(./**)"]
  }
}

Read-only credentials

  • A dedicated role with SELECT only, on the schemas in scope. The database enforces this even if every layer above fails.
  • Read-only transactions by default, a per-statement timeout and a connection cap, all set on the role itself.
  • The password is held by the MCP server and never placed in the model's context.
CREATE ROLE dq_reader LOGIN PASSWORD '…';
ALTER ROLE dq_reader SET default_transaction_read_only = on;
ALTER ROLE dq_reader SET statement_timeout = '30s';
ALTER ROLE dq_reader CONNECTION LIMIT 2;
GRANT USAGE  ON SCHEMA sales TO dq_reader;
GRANT SELECT ON ALL TABLES IN SCHEMA sales TO dq_reader;

Limited quotas

  • Per query: 30 s, 1,000 rows returned.
  • Per run: 200 queries, 60 agent steps, 45 minutes.
  • Per container: 1 CPU, 1 GB RAM, a read-only root filesystem, no added Linux capabilities.
  • Reaching a quota ends the call cleanly with a quota error, which goes to the fallbacks.
docker run --rm \
  --network dq-db-only \
  --read-only --tmpfs /tmp \
  --cpus 1 --memory 1g \
  --cap-drop ALL --security-opt no-new-privileges \
  dq-toolbox:1.4
