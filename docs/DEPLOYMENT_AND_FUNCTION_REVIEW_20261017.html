Deployment, persistence and functional review

This review records the controlled replacement of the DSH application runtimes and tests of the resulting behavior. It keeps operational evidence separate from the three-risk control design. Passing these checks does not remove an explicitly retained remote-execution exposure or establish every user's data permissions.

What was replaced

Twenty main DSH runtimes were replaced sequentially using their qualified pinned application image and existing read-only policy overlays. Each replacement required an idle agent check, a saved deployment specification, before/after file fingerprints, original history IDs and two temporary durable markers. Images, volume claims, mount paths, ownership and network policies were preserved. This was a process redeployment, not a new application-image build or storage migration.

The environment gateway, internal resolver and both owner-only legacy instances were also replaced. Gateway account/settings bytes survived. Legacy owner login, history listing, logout and real terminal WebSocket execution passed after replacement. The gateway source and managed inference transport were compared with repository contents; image digests and effective client policy were read back from the running workloads.

The broader review then found that DSH2/DSH3 advertised 1M without the qualified SDK output-budget loader. Their installed SDK reduced a high-character input's output allowance to one token. Both received the same immutable managed transport as the main service. Their installed clients also needed the managed policy and a dedicated model-scoped credential. The legacy harness rollout attaches those read-only settings and credentials without modifying account passwords or data permissions. /state for those clients is an alias of the same existing owner-only durable home volume, not replacement storage or a move of DSH histories; DSH's existing history path remains unchanged. Full-size legacy-specific 1M requests are not inferred from a configuration label.

The fresh GPU startup and near-1M experiment is recorded separately in fresh model acceptance. That coordinated test used the existing node, four GPUs and cached weights. The broader CPU rollout did not restart the GPU process, replace the database or rebuild unrelated infrastructure.

Data and history preservation

Across the twenty main runtimes, 31,897 regular files and 10,257,934,187 original bytes were checked, with no content failures. Original history IDs remained present: the legacy owner retained 80 histories, and the separately authorized admin copy retained 83 histories including its pre-existing records. Owner data was not reassigned. The two legacy runtime checks verified another 6,732 and 4,551 files.

The fingerprints cover mounted workspaces, session files and attachments. Lock files are excluded; symlinks are checked as links without following them into unrelated storage. Append-only growth is distinguished from a changed original prefix. These checkpoints verify preservation across this replacement; they are not an independent backup, deletion-recovery service or proof of every historical conversation's future tool resumption. Private paths and conversation contents are not published in the summary.

Mixed-load performance

The current-source DSH request counted 263,691 input tokens, returned the complete expected reply and persisted it in 274.01 seconds, with zero retries. The full 1,048,576-token ceiling, 8,192 output ceiling and 256-token reserve remained in place. One expensive request is admitted at a time; ordinary work remains concurrent.

Two additional natural-language replies correctly distinguished configured tools from verified connectivity. The worst recorded paired stream gap was 779 ms: scheduling improves opportunities, not uninterrupted decoding or a latency guarantee.

The final current-source DSH capacity retest counted 1,007,702 input / 119 output tokens, returned the complete expected 1–40 sequence and persisted it in 2088.27 seconds, with 2 retries. 60 ordinary DSH replies completed exactly alongside the active long turn in 5.06–8.66 seconds. This is capacity/transport/output-budget acceptance, not a new realistic analytical-quality review or two-full-1M test. The successful attempt included 243.67 seconds of admission wait and 1,227.76 seconds of preparation; the answer then streamed in 3.51 seconds (approximately 33.65 output tokens/second). The whole-turn duration also includes the preceding busy retries. These are different measures, not 34 minutes of decoding. The original combined zero-retry/latency gate did not pass and its raw result is retained. The long turn encountered occupied admission capacity before retrying; these timings include that wait. A correct eventual answer is not relabelled as a zero-retry cold run.

Sanitized measurements · Detailed short-response tracing lessons

Failures, corrections and lessons retained

  1. Historical slow reply versus reproduced cause. The old 38-second reply lacks a matching retained server trace. Fresh direct-backend measurements reproduced long-prefill interference, while matched forwarding/DSH timing records distinguish upstream arrival from delivery. Do not retroactively assert the exact cause of an untraced historical turn.
  2. Foreground wake-up race. A waiter could observe an idle event that a new foreground request had already invalidated. Rechecking active foreground work within the same bounded deadline closes that race. Tokenization itself now holds a temporary foreground lease. Long work retains its opportunities; the context ceiling was not reduced.
  3. A queued request is not actively preparing a prompt. An earlier 263K test encountered the 300-second admission deadline, retried once in DSH and eventually returned correctly after 526.31 seconds. Its original record is retained. It is not retry-free acceptance, and short requests overlapping that interval must not automatically be attributed to that queued prompt's GPU work.
  4. A successful test harness flag can be too broad. That earlier runner did not include long-request retries in its aggregate pass condition. The subsequent acceptance requires zero long retries. Saved individual retry counts take precedence over the older aggregate flag.
  5. Fixture authentication must match deployed storage. An old isolation fixture pointed the mutable password store at a read-only Secret. The corrected fixture seeds salted records into a distinct writable synthetic auth volume; the original Secret remains read-only. The initial failed fixture was isolated from Production.
  6. Installed policy overlays matter. A disposable pod copied from an older specification omitted the newer managed-client policy mounts. Its base-image Claude default was therefore not the effective main-service default. The current-overlay canary and all twenty live defaults were checked; the initial diagnostic is retained rather than treated as a Production regression.
  7. Qualification dependencies are different from application dependencies. The runtime does not include the operator's Python YAML test dependency. The full Python suite ran in the existing Linux qualification environment instead. Installed SDK/client tests ran in the actual runtime. Missing Windows/Linux paths are not application failures.
  8. Choose the replacement pod, not the first list entry. The gateway verifier initially selected an old terminating pod and restored the saved specification conservatively. Selecting a non-terminating, ready replacement with a different UID resolved the harness issue; the subsequent content/auth checks passed. The rollback did not overwrite data.
  9. Compaction must reduce context. At the artificial 2% threshold, a second summary would have increased a small shadowed range from 472 to 476 estimated tokens. DSH refused that redundant operation; the earlier summary and all three exact replies remained intact. Retain this distinction from an exception that prevents a user turn from completing.
  10. Coordinate the complete agent turn. A GPU or gateway maintenance boundary must account for tool continuations and client work between individual HTTP requests. The related fresh-GPU report retains a retry-bearing tool continuation interrupted by a gateway handover. A free long-request lease alone does not establish that every agent is idle.
  11. A profile label does not install its supporting loader. The legacy profiles declared 1M but the installed SDK still returned a one-token allowance for the high-character fixture. The qualified transport overlay corrects budgeting only for the managed internal aliases and leaves explicit smaller caller caps intact. Legacy client policy/credential/state wiring is verified separately from that DSH loader.
  12. A mounted Secret is not necessarily readable by a non-root process. The initial legacy harness mount used mode 0440 without a pod fsGroup and the actual client failed with EACCES. The corrected 0444 projection is mounted read-only only in that owner's execution container; auth and audit containers do not receive the volume. It does not make the key writable or mount it in another user's runtime. This avoids a volume-wide ownership change to existing data. Actual key reads, denied writes and client calls are release checks; file existence alone was insufficient.

The admin dashboard snapshot was refreshed after the tests and its mounted JSON was read back exactly. It now shows the current main/legacy boundaries and queue-bearing final result; the old shared-root legacy statement was removed. Gateway password and missing-runtime refusal checks passed after replacement. A positive live admin-browser login was not repeated; admin role/rendering coverage is from the separate regression fixture. All 26 requested active deployments were Ready at final readback. The model UID/image and zero restart count were unchanged. Four allowlisted disposable test pods were removed only after their synthetic session archives were downloaded, reread and independently hash-verified.

Risk-control conclusion

The seven HTML documents have different roles: the three-risk design, LLM setup/results, this deployment review, fresh-GPU acceptance, BrowserCode comparison, accepted realistic repository review and its preserved earlier editorial version. Historical or frozen-source reports remain recorded evidence, not current configuration dashboards. All seven are rendered in three viewport sizes; that does not reaccept their historical tests or change their original output.

The risk report remains organized around external leakage, damage/excessive access and result exposure, with control mechanisms and responsibilities. It does not embed test logs, migration diaries or performance tables into that narrative.

The application rollout preserves private execution, central persistence, named authentication and local restricted egress. It does not close the accepted remote Livy/Spark public-egress path, establish sandbox-only datalake grants, replace existing AD rights with read-only access, provide endpoint DLP, rotate owner-retained passwords or create independent storage recovery. Those boundaries cannot be closed by editing a report or restarting the application.

Rollback specifications and private fingerprints are retained. On regression, restore the reviewed workload/policy specification, compare actual content and retain newer writes; do not copy an older local tree over the mounted central workspace. Disposable test histories are archived and independently hash-checked before their pods are removed.
