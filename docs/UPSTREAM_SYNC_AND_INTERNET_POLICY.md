# DSH upstream maintenance and release policy

## Candidate port and automatic source review - 19 October 2026

This working candidate ports reviewed source to `0.2.1-rc.2`; Production acceptance and deployment remain separate. Earlier reviews below are historical pre-port evidence. Read the checked-out Dockerfile, current patch manifest and qualification receipts for candidate identity.

Daily/manual discovery now downloads public allowlisted npm archives as data before build and compares every target in `scripts/upstream_patch_contract.json`. Root and module archives require SHA-512 verification and package identity/version checks. Exact official dependencies are resolved through a bounded graph, including transitive modules under dsh-base. Receipts distinguish compatible, changed, missing, missing-package, unresolved-version and changed-package-contract targets with expected/actual hashes. A candidate version must also match the reviewed contract before build can proceed.

Detection rejects redirects, other hosts, excessive time/bytes, traversal, duplicates, links and special archive files. It never extracts or executes package code. Inspection errors produce blocked receipts. `candidate-evidence/source-diff.json` gives the paths and next action; an unreviewed release fails before Docker build. Review changed targets, adapt overlays and tests, and prepare a complete reviewed port PR. Automation never approves hashes or updates contracts.

The former automatic pin-only proposal job is removed. Scheduled detection and reviewed-source qualification remain automatic with read-only permissions and checkout credentials disabled. Complete upgrade PRs require human source review. There is no automatic merge, image publication or deployment.

### What our implementation actually is

The official npm application is the base. Kubernetes isolation, gateway authentication, central storage, access audit, package promotion and shared inference are separate deployment overlays. Ten bundled DSH files are modified by `configure_models.js`. The managed SDK budget loader, Claude/TrueForge policies and GPU scheduler patches belong to their respective dependencies, not to an upstream DSH source merge. We do not maintain a fully synchronized clone of the official monorepo.

The [patch inventory](UPSTREAM_PATCH_INVENTORY.md) separates these responsibilities. The new [versioned patch export](../patches/README.md) records the ten actual upstream/local differences, original and resulting hashes, and the configurator hash. The neutral-host diff is a review artifact; the guarded configurator remains the single runtime build-time application engine. No manual patch should be applied to a running installation. Supported plugins/configuration should replace individual source edits when equivalent upstream extension points are qualified.

### Update sequence

1. Detect npm latest and record source/channel/integrity metadata. An explicit preview remains opt-in.
2. Build a candidate from that exact official package. Keep local overlays separate. A changed contract stops automation rather than auto-approving new hashes.
3. Review upstream diffs, remove patches already supplied upstream, adapt required patches and tests, and regenerate the reviewed export.
4. Qualify actual installed code, authenticated web/RPC/Host boundaries and overlay regressions, then copied-state histories/attachments, tools, terminal/WebSockets, compaction, user/environment/network boundaries and rollback.
5. Publish an immutable candidate and perform a controlled handover only after the affected release checks pass. Preserve original histories and newer writes. A scheduled check or passing source test is not itself a Production upgrade.

This review changes candidate-build source and documentation. It does not upgrade the currently running DSH package or restart a shared service. Concurrent admission work has a separate owner and acceptance record.

## Why this is not a fully synchronized source fork

`dsh_setup` packages the official npm distribution and maintains deployment, authentication, routing, storage and model-configuration overlays. It does not copy the official monorepo. Updating the official package and preserving these overlays is the correct synchronization operation; merging all official source files into this deployment repository would mix two different repository purposes.

## Automated checking and candidate patching

The expanded `.github/workflows/upstream-candidate.yml` and its [tracked reference](UPSTREAM_CANDIDATE_WORKFLOW.yml) define:

1. Daily release checks at 02:17 UTC (09:17 ICT), manual dispatch, and checks on relevant source pushes/pull requests.
2. Scheduled and manual discovery track npm latest by default. A manual `candidate_version` can explicitly select a preview. Push and pull-request CI instead qualify the checked-out Dockerfile pin; newer npm releases are still reported in detection evidence.
3. A data-only source comparison runs before build. Matching reviewed candidates continue to Docker qualification; unreviewed or changed releases persist actionable receipts and fail before build.
4. Pre-patch SHA-256 contracts for all ten upstream files our configurator mutates. The reviewed baseline hashes were derived from official npm package archives after SHA-512 integrity verification. Changed/missing targets stop the build; the automation never updates those hashes for itself.
5. 7. Thirty-day build, package, test, image-ID and browser evidence artifacts plus a workflow summary. Failure blocks the proposal and is visible as a failed Actions run; no external notification service is configured.
8. No auto-merge, registry image publication or Production deployment in this GitHub workflow.

## Why Production upgrades remain gated

Our compatibility layer still modifies selected package files. The 0.2.1-rc.2 candidate has ten reviewed source inputs: two image-handling mutations and eight protected, unmodified upstream files. These hashes and candidate checks do not cover every future upstream semantic change. A changed target requires reviewing the source diff, adapting the overlay/tests and explicitly updating the reviewed contract. Prefer supported configuration/plugins over text patching as extension points become available; that migration is not complete.

Before deployment, qualify copied-state session reads, new prompts, compaction, attachments, tools, browser Host/Origin handling, HTTP/WebSocket terminal/application proxy, private-user/network boundaries and restart/restore. Review any unmatched patch target. Retain a compatible old image/configuration and coherent state recovery baseline. Read back the actual running image and test the affected behavior after cutover.

A passing build is a candidate result, not migration or Production acceptance. Never overwrite newer workspace/history data just to roll back an image.
