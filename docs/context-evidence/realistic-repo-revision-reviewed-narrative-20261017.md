# DSH 1M Context Guard: Execution Path, Admission, Latency and Compaction

## 1. Scope and evidence classes

This review covers the frozen DSH repository at its CURRENT HEAD. Four evidence classes stay distinct: frozen implementation/configuration (executable source and manifests); recorded test observation (captured evidence and assertions); historical checkpoint (dated documents that may contradict CURRENT); and recommendation. CURRENT means the frozen repository version as supplied; it does not establish fresh deployed behavior, and this review changed and tested nothing. No benchmark or SLA is invented here. The gateway budget is defined literally in source: `CONTEXT = 1048576` [S0308:L19-L19], `OUTPUT = 8192` [S0308:L20-L20], `RESERVE = 256` [S0308:L21-L21], and `LONG_THRESHOLD = 131072` [S0308:L22-L22]. Compaction values come from the runtime-policy configurator, which selects `thresholdRatio: context === 1048576 ? 0.875 : 0.75` [S0005:L30-L33]. Prose elsewhere describing 128K budgets or a 98,304-token compaction point is a historical checkpoint, not current policy. This review establishes no SLA.

## 2. Execution path and the warming mismatch

The frozen path is authenticated user to private DSH runtime, then internal LiteLLM, then the two canonical DeepSeek aliases through a loopback-only guard and forwarder before SGLang [S0346:L110-L110]. Promotion rewrites canonical routes to the loopback guard [S0304:L54-L60] and defines the loopback `context-forwarder` sidecar [S0304:L87-L89] and appends it to the pod container list [S0304:L100-L100]. The alias guard rejects endpoint overrides and clamps output with `data['max_tokens'] = min([8192]+limits)` [S0367:L13-L21]. The admission guard tokenizes through the running backend, uses the configured tokenizer endpoint [S0308:L43-L48], validates the returned model limit and exact token IDs [S0308:L62-L68], and refuses dispatch when counting fails [S0308:L180-L184]. The forwarder counts the final envelope and returns 503 if budgeting is unavailable rather than estimating [S0196:L88-L91].

The recorded cause of the warming mismatch was a defaulting divergence: the tokenizer materialized an omitted tool default differently from inference, so a request counted 7,689 tokens but inference processed 7,561 [S0346:L130-L130]. CURRENT normalizes both: `continue_final_message` defaults to false [S0272:L5-L5] and the omitted function `strict` is materialized as false [S0272:L12-L12]. The forwarder applies that normalization before counting [S0196:L85-L85]; the callback counts the final envelope while preserving messages, tools and template options [S0308:L34-L42]. Explicit caller values are preserved [S0279:L167-L173].

## 3. Long-request admission versus ordinary concurrency

Admission is not a global concurrency limit. A request is long when counted input plus clamped output exceeds `LONG_THRESHOLD` [S0308:L198-L198]. Only long requests take the shared lease; ordinary requests do not wait on it [S0308:L1-L5]. The lease is a non-blocking `flock` with a 300-second deadline [S0308:L144-L148]; on exhaustion the code raises an HTTP 429 carrying a retry hint [S0308:L150-L154]. The recorded admission test held that lease deliberately and observed a real 429 while ordinary DSH replies continued, with release then allowing a 140,034-token request [S0346:L24-L26]. Retry policy targets only the two loopback-guarded groups [S0304:L19-L28]. Handover uses one replica and Recreate [S0304:L44-L45]: that is an intended single-writer arrangement, not proof that overlap is impossible under all circumstances, and the record notes that multiple replicas would require distributed ownership [S0289:L50-L50]. Ordinary concurrency is bounded by backend arguments such as the running-request ceiling [S0280:L89-L90].

## 4. Cold versus cached latency, and memory

Cold, cached and decode measurements are different quantities. The recorded cold DSH near-1M completion is 1,007,689 input tokens in 1,170.08 seconds with zero retries and no restart [S0346:L152-L152], and the CURRENT README records the 19m34s cold reply [S0087:L5-L5]. The same-session tool continuation at 1,008,103 input tokens passed in 20.16 seconds [S0087:L5-L5]. Cached continuation is distinct: a recorded 257,738-token follow-up returned in 2.04 seconds, labelled hot-prefix reuse [S0346:L151-L151]. Recorded mixed-load qualification shows short replies completing in 0.477-0.613 seconds during a 120,049-token request that itself took 35.67 seconds [S0346:L46-L46]. The recorded current-image window shows 1,132 recovering allocator warnings and a minimum warning-reported free memory of 1.75 MiB [S0346:L48-L48].

The recovery path is layered. A bounded probe (`CACHE_PROBE_SECONDS = 2`) [S0308:L27-L27] attempts to reuse a continuing conversation's prefix in one short call; an acknowledged timeout abort becomes `CacheProbeMiss` [S0308:L91-L95], which the warming routine catches before entering incremental preparation [S0308:L115-L126]. Incremental warming then extends the prefix in `WARM_STEP = 2048` token steps [S0308:L26-L26], checking cache reuse after each step and failing closed if the prefix was evicted rather than repeating a monolithic prefill [S0308:L127-L138]. That separation matters operationally: the probe is a cheap reuse test, while the stepwise loop is the actual cold-prefill mitigation, and its cost is paid in extra internal model calls rather than user-visible output.

On resources, the model container sets `--mem-fraction-static` to 0.90 [S0280:L87-L88] and enables the Engram host-table offload with pinning and KV prefetch [S0280:L113-L120]; the container requests 256Gi of host memory and limits it to 512Gi [S0280:L133-L141]. That 512Gi is a container host-memory limit, not GPU memory; KV cache and temporary attention workspace are separate GPU resources. The historical failed trial records a real ~262K request failing with CUDA out-of-memory [S0219:L18-L18]; the recorded diagnosis explains that slot arithmetic omitted temporary attention workspace [S0219:L41-L42]. The observed failure row alone does not establish that diagnosis, so both are cited.

## 5. Compaction and prior-test limits

The 1M compaction policy yields a normal calculated trigger of 917,504 estimated tokens [S0346:L195-L199]. That is a configuration calculation, not a fresh successful compaction of a historical session. Pressure is estimated between agent steps while the proxy counts exactly on the final wire, and a large single tool result may reach the request guard before auto-compaction, in which case overflow is refused [S0346:L201-L201]. A recorded fixture with a lowered trigger exercised the real automatic path and validated summary persistence and recall, explicitly without certifying every historical session [S0289:L60-L60].

Prior tests state their own limits. The older 105-response stress campaign belongs to the 128K baseline; its 16-request throughput must not be read as 16 concurrent 1M capability [S0289:L68-L68]. The historical backend-only 1,000,015-token success belongs to an earlier scheduler profile and is not proof of end-to-end DSH operation [S0346:L68-L68]. Later recorded end-to-end DSH passes do exist and are cited above, but the current record still lists unqualified items: sustained soak, two full concurrent 1M requests, full output at near-maximum input, near-1M vision and semantic-quality assessment [S0346:L106-L106]. The recorded transport retest used a delayed synthetic endpoint without GPU inference [S0346:L187-L187], and the recorded 429 validated admission behavior rather than two real near-1M GPU requests [S0346:L102-L102].

## 6. Routing, reconciliation and operational workflow

Private routing is conditional in CURRENT implementation, not merely diagrammed. When a provisioned per-user target file is present, each identity and per-environment target is validated for host, port and token path [S0240:L103-L112]; selection then returns that fixed target for the authenticated identity and environment [S0240:L115-L123]. When that file is absent the code falls back to the environment-wide default targets [S0240:L122-L122]. A missing identity or environment mapping is refused at login [S0240:L787-L790]. A published diagram is not verification of live routing.

The admission guard and the forwarder also impose different deadlines on the same long request, and they should not be conflated. The forwarder applies a 15-second first-output deadline during long-context cache handoff [S0196:L152-L152], while the client-side transport waits are governed separately by a test fixture that asserts one-hour header/body timeouts for the managed origin and unchanged options for its listed unrelated origins [S0357:L5-L12]. A client transport timeout therefore does not by itself describe handoff behavior, and a successful handoff does not prove the client deadline was exercised. The compaction and admission settings are declared configuration; only a recorded run shows behavior.

Operationally, promotion is single-writer: the runtime controller requires `Recreate` and a single replica [S0010:L62-L62]. The gateway candidate requires one replica [S0304:L40-L45]; a separate readback refuses deployment if its current specification changed after planning [S0304:L151-L153]. Promotion requires actual near-1M acceptance evidence before applying [S0304:L140-L147]. The candidate asserts that its volume specifications and mount list are unchanged [S0010:L70-L71]. Separately, the rollback initializer verifies the saved profile hash, replaces the profile and reads it back for byte equality [S0010:L46-L51]. The backup branch saves profile bytes, hash and readback [S0010:L39-L43], and the initializer mounts the existing state volume [S0010:L55-L58]. This is implemented behavior and recommended procedure from source review, not a fresh executed test, and it cannot guarantee against overwriting newer data in every failure mode.

Post-cutover verification should distinguish declared settings from observed behavior. The promotion path does check the persisted ConfigMap content against the intended data and confirms the mounted configuration name [S0304:L156-L161]. Separate assertions in the promotion code require an exact inference response and rejection of a client endpoint override [S0304:L169-L175]. Reading back the running image ID is not performed by those spans and is therefore stated here as a recommendation rather than a verified step. Historical 128K statements describe an earlier deployment in which the backend ceiling had been raised while product guardrails remained lower [S0346:L9-L9]; the current executable budget is 1,048,576 [S0308:L19-L19]. Where evidence is insufficient, the correct statement is that the claim is not established.
