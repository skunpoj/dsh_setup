Current release

DSH 0.2.2-rc.1 is built into the runtime image that every user workspace runs (image 66f6a04d since the 10 Nov 2026 rollout). User and environment storage mounts stay in place when an image is replaced, so saved files and histories are kept. See the speed comparison for the current inference profile and measurements. Native /compact and automatic step-pressure compaction work with the internal model and preserve the original events and a readable summary; keep that functional check separate from near-1M performance and pressure tests.

Reviewed port and automatic source review

The reviewed port pins the package, preserves authentication/routing overlays and adapts the SDK transport and managed model defaults.

Daily/manual discovery now downloads public allowlisted npm archives as data before build and compares every target in scripts/upstream_patch_contract.json. Root and module archives require SHA-512 verification and package identity/version checks. Exact official dependencies are resolved through a bounded graph, including transitive modules under dsh-base. Receipts distinguish compatible, changed, missing, missing-package, unresolved-version and changed-package-contract targets with expected/actual hashes. A candidate version must also match the reviewed contract before build can proceed.

Detection rejects redirects, other hosts, excessive time/bytes, traversal, duplicates, links and special archive files. It never extracts or executes package code. Inspection errors produce blocked receipts. candidate-evidence/source-diff.json gives the paths and next action; an unreviewed release fails before Docker build. Review changed targets, adapt overlays and tests, and prepare a complete reviewed port PR. Automation never approves hashes or updates contracts.

The former automatic pin-only proposal job is removed. Scheduled detection and reviewed-source qualification remain automatic with read-only permissions and checkout credentials disabled. Complete upgrade PRs require human source review. There is no automatic merge, image publication or deployment.

Upgrade procedure and history recovery

Use the reviewed image and compatible transport/profile overlays together. A package upgrade alone can leave a retained profile pointing to an alias its managed key cannot use. The profile migration helper changes managed model defaults and retains the original profile; it does not change credentials, workspace files or conversation events.

  1. Check actual running versions, image digests, mounts, active agents, notebooks and app-supervisor state. Qualify a separate private runtime first.
  2. Stop that runtime's writer gracefully. Save its complete deployment specification and a coherent private copy of state, workspace metadata, attachments, credentials and settings. Do not use a live directory copy as an atomic backup.
  3. Export history with a compatible installed reader, then import into a new, absent directory. Preserve raw originals and verify logical IDs, headers and events after reopening in another process.
  4. Start the reviewed image with its matching transport and profile helper. Preserve the existing user/environment mounts, approval settings, quotas and account store.
  5. Test actual login, session opening in registered workspaces, a saved file and attachment, tools, application restart and cross-user denial. Register missing project paths through Add workspace; do not move history to fix a display filter.
  6. Upgrade one runtime at a time. Update the capacity controller's future-runtime template only after qualification so signup cannot create an incompatible worker.

Lossless export and import

These commands run inside a private operator environment containing a stopped-writer copy. Supply the installed module path for the compatible DSH release. Archives contain private conversations and must never be committed or published.

node scripts/session_archive.mjs \
  --action=export \
  --modules=/usr/local/lib/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai \
  --private-base=/operator-private \
  --source=/operator-private/copied-state/sessions \
  --attachments=/operator-private/copied-state/attachments \
  --quarantine=/operator-private/copied-state/quarantine \
  --archive=/operator-private/export-unique \
  --compression=zstd

node scripts/session_archive.mjs \
  --action=import \
  --modules=/usr/local/lib/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai \
  --private-base=/operator-private \
  --archive=/operator-private/export-unique \
  --target=/operator-private/restored-unique \
  --compression=zstd

Use --name=value arguments. Export and target directories must be new and separate. The helper refuses corrupt members, duplicate IDs, overlapping paths, links, unsupported inherited prefixes and existing destinations. Its bounds are 64 MiB per file, 1 GiB total, 10,000 sessions and one million events. A refusal requires operator review; it must not be bypassed by editing or dropping events.

The 20 October qualification preserved 80 original histories and 6,656 events. A forward-recovery case retained 81 histories and 6,661 events, including new working-directory/job events, attachments and quarantine material. Originals remained unchanged. This validates these recorded formats, not arbitrary future event schemas.

Recovery after the newer writer has run

The older 0.2.0 reader rejects a newer required working-directory event. An image-only downgrade is therefore unsafe after new writes. Retain the new state and use the compatible reader/export/import path above. Never overwrite it with an older snapshot or strip required events. Restoring a saved deployment specification is separate from restoring data; reopen the recovered histories and verify actual browser visibility before changing routes.

Operational lessons for upgrades

  • Preserve the workspace registry as well as session files. A fresh, unregistered test workspace can show an empty picker while the histories remain readable. Expand each registered project's Show more controls when checking older conversations.
  • Export only a coherent stopped-writer copy. The helper refuses an export whose source changes during the copy, which prevents an inconsistent archive.
  • Record the activation boundary before changing an image. If the cluster API connection fails, inspect actual pod image, state and writer activity before retrying. A failed client response does not establish that the server-side operation did not occur.
  • Keep monitoring separate from the agent's work. If an observation connection fails, recover the completed turn from persisted events and tool output without submitting a second prompt. A monitoring failure is not itself an inference failure.
  • Replace disposable test workers before touching user-facing workers. Recheck actual application replies, persistent Stop, private history denial, existing mounts and approved startup definitions after replacement.

Official release and model update proposals

Automatic runs now save release-candidate.patch and release-proposal.json before the reviewed-source execution gate. A newer release generates a minimal candidate pin patch, but it remains incomplete and blocked until its full source port, contracts, SDK and regression tests are reviewed. The workflow never applies the patch, approves new hashes or deploys it.

Official model tracking reads only DeepSeek's public pricing/model table and changelog. New revisions require changelog corroboration; malformed or ambiguous documents fail closed with a saved receipt. config/official-deepseek-models.json records official API aliases separately from dated revisions. official-model-update.patch changes that tracking metadata only, preserving all runtime routing, credentials and catalog defaults. It does not call inference or query authenticated APIs.

The reviewed official snapshot on 19 October 2026 identifies deepseek-flash as DeepSeek-V4.1-Flash-1017 and deepseek-v4-pro as DeepSeek-V4-Pro-0813. These are official API observations, not evidence that our internal LiteLLM backend runs those revisions. Model deployment/routing changes require independent backend and capability qualification. No context, output budget, price or vision capability is automatically increased from a public announcement.

Nine regression cases cover model revision proposals, retained API aliases, missing/ambiguous documents, new-revision corroboration, URL restrictions, unchanged releases, stale/mixed receipts, unsafe versions, and preservation of existing Dockerfile commands. Synthetic future-release fixtures test patch generation; they do not claim a newer official DSH release exists.

Account provisioning overlay

Self-service signup and administrator Internet approval are gateway deployment overlays, separate from the upstream application. Preserve account-store slot assignments, the qualified read-only signup catalog and per-user mounts during updates. Run the routing test entrypoint, including self-registration regression checks, and qualify candidate signup/persistence before changing the published pool. Never reset account state or replace assigned private storage during an upstream upgrade. See self-service setup and replenishment.

Update sequence

  1. Detect npm latest and record source/channel/integrity metadata. An explicit preview remains opt-in.
  2. Build a candidate from that exact official package. Keep local overlays separate. A changed contract stops automation rather than auto-approving new hashes.
  3. Review upstream diffs, remove patches already supplied upstream, adapt required patches and tests, and regenerate the reviewed export.
  4. Qualify actual installed code, authenticated web/RPC/Host boundaries and overlay regressions, then copied-state histories/attachments, tools, terminal/WebSockets, compaction, user/environment/network boundaries and rollback.
  5. Publish an immutable candidate and perform a controlled handover only after the affected release checks pass. Preserve original histories and newer writes. A scheduled check or passing source test is not itself a Production upgrade.

This review changes candidate-build source and documentation. It does not upgrade the currently running DSH package or restart a shared service. Concurrent admission work has a separate owner and acceptance record.

Why this is not a fully synchronized source fork

dsh_setup packages the official npm distribution and maintains deployment, authentication, routing, storage and model-configuration overlays. It does not copy the official monorepo. Updating the official package and preserving these overlays is the correct synchronization operation; merging all official source files into this deployment repository would mix two different repository purposes.

The Dockerfile pin, and the DSH package in the private workspaces as of 10 Nov 2026, is 0.2.2-rc.1. scripts/check_upstream.py compares it with the official npm channels on a schedule and never applies a newer release by itself. The source HEAD of the official repository and its published package release are separate facts: the package metadata does not provide a gitHead mapping.

Upstream describes DSH as developer-preview software with breaking changes. See the official README and safety guidance.

Current automated checking and reviewed candidate qualification

The expanded .github/workflows/upstream-candidate.yml and its tracked reference define:

  1. Daily release checks at 02:17 UTC (09:17 ICT), manual dispatch, and checks on relevant source pushes/pull requests.
  2. Scheduled and manual discovery track npm latest by default. A manual candidate_version can explicitly select a preview. Push and pull-request CI instead qualify the checked-out Dockerfile pin; newer npm releases are still reported in detection evidence.
  3. A data-only source comparison runs before build. Matching reviewed candidates continue to Docker qualification; unreviewed or changed releases persist actionable receipts and fail before build.
  4. SHA-256 contracts cover ten reviewed source inputs in the 0.2.1-rc.2 candidate: two image-handling mutation targets and eight protected, unmodified upstream files. The reviewed hashes were derived from official npm package archives after SHA-512 integrity verification. Changed/missing targets stop qualification before build; automation never updates reviewed hashes for itself. The actual installed-package guard also verifies the reviewed inputs before configuration.
  5. Actual installed-module syntax/budget/profile checks, disposable DSH web startup and session/model-catalog RPC, anonymous/Host denial, gateway routing and forged-header tests, package promotion, Python rollback/manifests tests, and browser admin-dashboard and installed upstream-client checks. The actual runtime smoke test has no network or Production storage. The test directory is now included in the Docker context; its earlier exclusion was incompatible with the Dockerfile's test copy.
  6. Human review of a complete source-port PR is required for upgrades. The former automatic pin-only proposal job is removed; the current workflow has no write-capable job.
  7. Thirty-day build, package, test, image-ID and browser evidence artifacts plus a workflow summary. Failure blocks qualification and is visible as a failed Actions run; no external notification service is configured.
  8. No auto-merge, registry image publication or Production deployment in this GitHub workflow.

Current workflow permissions and scheduling

The current workflow requires GitHub Actions execution with contents: read; it disables persisted checkout credentials and has no write-capable proposal job. It does not require the repository setting allowing Actions to create pull requests. Reviewed source still qualifies when the selected version is unchanged. Complete port PR creation and human review occur separately. Scheduling runs the workflow from GitHub's default branch; the tracked documentation reference is not another scheduler. Repository policy may require approval before a contributor's PR workflow executes. See GitHub trigger rules.

Verification scope

  • Official channel lookup validates the exact package name, version and SHA-512 integrity field; wrong package/version and missing integrity are refused by tests.
  • The patch-contract check accepts a reviewed fixture and refuses changed or absent targets. For the current candidate it protects ten reviewed inputs: two mutation targets and eight unmodified upstream files. It is not a semantic audit of every upstream dependency.

To reproduce detection locally:

python scripts/check_upstream.py --event schedule --output upstream-check.json --source-diff source-diff.json
python scripts/check_upstream.py --candidate 0.2.1-alpha.4 --output preview-check.json

--prepare-candidate permits a Dockerfile pin change only to the version already present in the reviewed source contract; it cannot prepare an unreviewed pin-only upgrade. Neither command installs packages into Production. Candidate version input is validated before registry lookup/preparation. Detection does not claim that text patches rebase themselves correctly.

Why Production upgrades remain gated

Our compatibility layer still modifies selected package files. The 0.2.1-rc.2 candidate has ten reviewed source inputs: two image-handling mutations and eight protected, unmodified upstream files. These hashes and candidate checks do not cover every future upstream semantic change. A changed target requires reviewing the source diff, adapting the overlay/tests and explicitly updating the reviewed contract. Prefer supported configuration/plugins over text patching as extension points become available; that migration is not complete.

Before deployment, qualify copied-state session reads, new prompts, compaction, attachments, tools, browser Host/Origin handling, HTTP/WebSocket terminal/application proxy, private-user/network boundaries and restart/restore. Review any unmatched patch target. Retain a compatible old image/configuration and coherent state recovery baseline. Read back the actual running image and test the affected behavior after cutover.

A passing build is a candidate result, not migration or Production acceptance. Never overwrite newer workspace/history data just to roll back an image.

Current enterprise responsibilities

Gateway sessions use a separate protected file beside the account store. It contains hashed session identifiers, identity/environment bindings, credential fingerprints and creation times; it contains no cookie bearer values. Owner-only permissions, atomic replacement and a server-enforced 24-hour lifetime apply. Logout and revocation persist across restarts. A malformed store refuses startup instead of silently resetting authentication. Run one gateway writer with Recreate deployment strategy; this file is not a distributed multi-replica session database. Keep the auth volume outside execution-worker mounts and preserve every existing source ConfigMap key when adding the session helper. The first migration from memory-only sessions requires signing in again; subsequent restarts retain valid sign-ins. Do not restore old account or session files just to roll back gateway code.

The inference gateway also has a small, separately maintained OpenAI streaming compatibility shim. Its purpose is to preserve the final-wire admission guard's HTTP 429 instead of converting that busy response into HTTP 500. It accepts only marked numeric 429 errors from the fixed loopback guard, checks the pinned SDK reader's source hash before startup, and leaves unrelated provider errors unchanged. Requalify this shim when changing the LiteLLM image or OpenAI SDK; updating the DSH package alone does not update that dependency. Run scripts/test_stream_admission_integration.py --output <new-private-receipt.json> and the HTTP retry-policy test against the installed candidate before handover, then verify the actual public response and DSH Stop behavior. Never disable the source check to make an unreviewed image start.

Private No Internet and Internet routing is deployed. thanatcc retains the original two runtimes and 80 legacy histories; admin now has its own private pair. Other users have private runtimes. Secure workspaces/durable state use bounded CIFS subpaths; credentials/configuration/tickets remain private local state. Internet uses separate local storage. The environments share inference and reviewed dependency artifacts, not writable projects or histories.

No Internet restricts local execution through infrastructure policy. A real remote Spark test demonstrated public TCP access from its driver and executor; the user explicitly chose to keep Livy/Spark available with that documented risk. The prepared containment patch remains unapplied. This is not solved by updating DSH. Existing AD/datalake permissions are preserved as instructed; universal read-only enforcement is not claimed.
