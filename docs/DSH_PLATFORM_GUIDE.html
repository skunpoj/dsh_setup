DSH Platform Guide

Current governed-harness architecture, feature coverage and document map for highly classified internal work in an isolated RKE2 environment. The platform fixes all managed runtimes to the internal LiteLLM route; users cannot select an external provider, endpoint, proxy or model credential.

Current entry point. This guide consolidates the current HTML documentation without merging DSH with another project’s document server. GitHub remains reviewed source and history; the DSH manual server is the intended user-facing host.

1 Governed Harness architecture

The wrapper supplies identity, workspace, policy, model routing, lifecycle, result ownership and audit. The runtimes execute tasks behind that boundary; they are not independent identity or authorization authorities.

Architecture 1 — identity, runtimes, backends and model route

Deployed/selectable

Web DSH, private workspace, SDK, Claude Code and Deep Agents are exposed by the running broker. Each runtime has one bounded Test marker reconciled to guard/server/spend identity.

Source-prepared or adapter target

Kilo and bounded handoff exist in reviewed successor source but are not verified live. TrueForge remains a separate owner-only application with an adapter target.

Fail-closed

OpenShell is disabled until all 25 live gates, rollback, namespace, node, budget and expiry controls pass.

5 Current limitations and acceptance boundary

  • OpenShell is not operational or credited as a current control until all 25 live Test gates and rollback pass.
  • Kilo, bounded cross-runtime handoff and the TrueForge adapter are not claimed as deployed behavior.
  • One bounded SDK, Claude Code and Deep Agents marker does not establish arbitrary tool, subagent, approval, cancellation or recovery acceptance.
  • Passing CI, Pod readiness, HTTP 200 or a rendered document does not prove private deployment parity.
  • Host-level peer-access changes, DeepEP qualification and new GPU benchmarks remain separate authorized work.
