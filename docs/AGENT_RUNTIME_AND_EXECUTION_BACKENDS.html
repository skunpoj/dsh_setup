Agent runtime and execution backend

For a detailed enterprise control matrix covering the Multiharness, DSH Python SDK, Claude Code, Deep Agents and their standalone counterparts, see Multiharness and managed runtime comparison.

This reference separates the deployed control plane from runtime capabilities that still require bounded live acceptance.

Decision frame. The primary question is not which agent has the longest feature list. It is whether each use of highly classified internal data remains inside an isolated RKE2 environment, uses only the fixed internal LiteLLM route, cannot broaden its own authority, and returns results only to the authorized owner. The three controlling outcomes are: (1) prevent external leakage, (2) prevent damage or excessive access, and (3) keep results contained. OWASP Agentic Top 10 is used as a supporting threat taxonomy, not as a replacement for these enterprise outcomes.

Available now

Authenticated Web DSH, Web Terminal and installed managed-client entry points operate in the user's assigned private workspace. The running /agent-tasks broker advertises sdk, claude and deepagents, and rejects unauthenticated requests. Reviewed successor source adds kilo and one bounded cross-runtime handoff; it is source-tested but not deployed. OpenShell remains disabled and is not user-selectable.

Web DSH compared with the Python SDK

Web DSH is the authenticated control surface: it chooses the runtime, project, write mode and execution backend, then displays state and output. The Python SDK is one runtime behind that surface: it creates the programmatic agent, invokes tools, saves its checkpoint and resumes an approved interrupt. Choosing it does not turn ordinary DSH chat into an SDK conversation and does not give the browser a model credential.

Standalone conclusion. Putting the same runtime in the same RKE2 cluster and forcing the same LiteLLM endpoint reproduces only part of leakage control. Without DSH AD/LDAP and the broker, each standalone SDK service, Claude Code service or Deep Agents service must independently rebuild human identity, task authorization, tenant storage, exact approval, cancellation, no-replay recovery, result sharing and audit correlation.

OWASP supporting crosswalk

The detailed comparison maps OWASP Agentic Top 10 risks to these three controlling outcomes in the linked full matrix. Goal hijack, tool misuse, identity abuse, supply-chain compromise, unexpected code execution, memory poisoning, insecure inter-agent communication, cascading failures, human trust exploitation and rogue agents can affect more than one of the three outcomes. The applicable response is therefore layered containment plus tested lifecycle controls—not a prompt-only safeguard or an OWASP label. This is an analytical mapping, not certification or proof that every risk is closed.

Deployed behavior and remaining acceptance boundary

The current gateway and broker are deployed. The reviewed successor adds Kilo, bounded cross-runtime handoff and correlation metadata, and its source tests pass. No successor image, Test deployment or live handoff has yet been verified. One-marker guard-to-LiteLLM reconciliation is accepted separately for SDK, Claude Code and Deep Agents. Full approval/resume, arbitrary tools, authenticated delegation, cancellation/recovery, immutable-image provenance, TrueForge adapter behavior and OpenShell acceptance remain unverified.
